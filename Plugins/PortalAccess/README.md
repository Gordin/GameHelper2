# PortalAccess

F12 → Maps & earnings → Portal interaction recovery offers an opt-in switch to restore targeting and highlighting on closed portal entities still resident in the current area. New configurations default to read-only; existing explicit preferences are preserved.

Recovery requires one of the verified 2026-10-05, 2026-10-06 or 2026-10-10 client instruction profiles. Each matched profile supplies its own vtable location. Four instruction-block hashes, the component vtable and the client's named diagnostic flags must all match. Only Targetable +0x69 and Highlightable +0x6A are writable. The inherited +0x51/+0x52 locations overlap a vector pointer and are never used for game writes. Unknown layouts remain read-only, even with the switch enabled. See [layout evidence](DIAGNOSTIC_LAYOUT.md).

Each write checks native loading, area pointer/hash, player identity and portal component ownership again. Only valid supported portal objects with a Portal component and satisfied quest/item conditions qualify. Each entity is repaired once per area, matching the reference behavior. Switching off attempts to undo this plugin's changes to the same current entities; area/session changes discard stale addresses without writing. Generic writable attachments remain restricted to own-process offline fixtures.

Discovery shares a 15 ms / 4,000-read budget. Each map processes up to 128 entity keys per sample; the next sample seeks the next key from the current root. No traversal pointer survives a sample. Awake/sleeping maps alternate priority, and partial candidate parsing is retried. Up to 128 found portals are retained even if later diagnostic reads exhaust the budget. Each page has a 2,000-node guard; large valid maps complete across multiple samples. Recovery has a separate 40 ms deadline checked between validations/writes; an in-progress validation can finish after the deadline but cannot write afterwards. Incomplete samples are reported. Diagnostics in config/ update every 10 seconds and include the matched profile and modified-field count.

The user reports successful recovery on the standalone client. A friend's Steam diagnostic also matched the same instruction profile, but its incomplete discovery found no portals; the paged-scanning fix awaits their test. Flag readback is not visual or server validation. Deleted entities or expired/rejected destinations cannot be recreated. No proprietary executable or authentication code is bundled. [Offline tests](../../Tests/README.md) never write to the game.

The 2026-10-06 update relocates the Targetable methods and vtable while leaving the two flag offsets unchanged. The updated client and resident closed portal passed read-only profile/identity checks; appearance and entry on this patch await the user's test.

The client inspected on 2026-10-10 changes the vtable location and two instruction-block hashes again, with the same verified flag offsets. Its separate profile preserves the existing recovery guards and earlier profiles. Actual appearance and entry require the user's in-game test after loading the updated plugin.
